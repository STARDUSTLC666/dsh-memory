# 检查反馈故障与统一版本修复

检查实际工具回执发现：`comparison-v3` 和 `independent-holdout-v2` 的 `project_check` 注册处理器仍调用 `grade.py`，而复制的文件只有 `grade_v2.py`。结果是回合内检查报文件缺失，模型没有收到可信的行为反馈。运行结束后控制器使用 `grade_v2.py`，所以仍能产生后验行为分数。仅验证结束评分器和 Memory bridge 的预检没有发现这个入口错误。

这是实验质量问题。旧开发、验证和已完成的部分留出分数、选择文件、代码及原始回执均不覆盖；标记为缺少回合内反馈的诊断，不能用于确认完整开发任务效果或候选有效性。旧候选选择失效，不沿用到修复后留出。

发现后停止旧留出启动器，保留停止时的未完成原始轨迹。`audit_check_feedback.py` 逐次统计实际 `project_check` 是否返回布尔 `passed`，工具错误与任务行为失败分开记录。

新目录为 `comparison-v4-feedback/{development,validation,holdout}`，版本为 `r5-v1.3-feedback`。唯一运行修复是 `project_check` 指向现有 `grade_v2.py`；控制器额外在检查工具错误时停止继续批次。评分器、任务真值、提示、预算、检索、Memory 算法和 A 来源图逐文件保持一致。开发和验证放在隔离目录并行运行，留出等待新验证集和新候选选择。

新预检通过实际 DSH SDK 注册的七个工具执行入口，逐组验证：初始实现返回失败、参考实现返回成功、隐藏真值读取拒绝、B 会话记忆写入拒绝。三个目录各六组全部通过。随后第一条真实 DSH 模型运行的工具回执也确实收到 `passed=false` 及契约失败信息，而不是文件缺失。

修复后的全部 A–F 重新运行，各版本不混合。部分相同留出任务已经在故障版本中暴露过输出，本次必须注明“评分工具修复后的统一重跑”，不能冒充未曾查看过的全新封存集。没有据故障留出分数修改算法或真值；仍仅用修复后的验证集重新选择候选，再确认或否定，不能重新挑留出赢家。
